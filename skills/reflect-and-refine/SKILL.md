# Reflect and Refine

Improve recurring work using evidence from actual tasks. Separate necessary iteration and useful exploration from avoidable rework. A long task or many revisions alone is not a defect.

## Review the work

1. Use the user's requested records, sources and time window. If none is specified, start with a small set of recent substantive work and state what you reviewed. Do not expand access or search unrelated material to fill a quota.
2. Inspect the selected work products, decisions, changes and results. Prior summaries can locate evidence; they do not prove the current result. State missing evidence and coverage limits.
3. For each useful finding, identify the objective, actual outcome, first material drift, cause, resolution and supporting evidence. Distinguish mistakes, changing requirements, genuine source blockers and normal exploration.
4. Recommend a durable fix only when the failure recurs or affects a high-value recurring workflow. Prefer an enforced structure or contract, then focused validation, then a small change to the existing workflow, instruction or prompt. Use the [fix-layer rubric](references/fix-layer-rubric.md) when several fixes compete.
5. Implement only when requested or already authorized. Preserve unrelated changes and test the behavior that originally failed. A review-only request returns proposals. Do not change retained preferences, schedules or external systems without separate authorization.

## Maintain skills and instructions

Identify the actual entrypoints, supporting files, owner, editable source, distributed copies and current content hashes. Check active work before changing instructions it may still read. Distinguish observed use from a catalog mention or inferred relevance.

Read the instructions and the dependencies that govern the behavior under review. Record a concrete keep, cut, move or fix decision; healthy skills can stay unchanged. Remove demonstrated conflicts, stale assumptions, duplicated policy and forced output ceremony while preserving source, privacy, quality and release requirements.

Keep one workflow owner. Improve an existing skill before adding another. A new skill needs a distinct recurring trigger, inputs, outcome and validation path.

Stage small changes with exact baselines and rollback copies. Test realistic positive, failure and recovery cases. Keep structural checks, instruction review and observed runtime behavior distinct. Recheck hashes before replacing files, preserve concurrent edits and verify the installed result. Shared distribution and publication retain their own ownership and authorization.

## Return what matters

Lead with the main finding and the practical change or recommendation. Include the selected evidence, coverage limits, exact owner, validation and remaining uncertainty. Use a short table when several parallel findings are easier to compare. Do not force scores or a large backlog when a concise finding is enough. If no durable change is justified, say so.
