# Manage work

Keep the user's intended outcome in view while implementation proceeds. Coordinate through the existing owner task and project records. Domain skills still own source accuracy, evaluation isolation, artifact quality and release requirements.

## Establish the current goal

Read the latest user requests and corrections, the existing plan/backlog, current artifacts, and any explicitly created goal. Verify source paths, active workers and unfinished operations before dispatching more work. Prior messages and progress summaries locate evidence; inspect the actual work product before accepting it.

Write a short working objective and identify the next useful milestone. Reconcile new requests with completed work: retain what is accepted, reopen only affected items, and surface a material scope conflict. Keep existing goal state honest; never mark unfinished work complete merely to replace a goal or satisfy a deadline. Loading this skill does not create a goal or a new tracker.

Use the existing backlog/ledger when it is usable. Track only what decisions need: outcome, state, owner, dependencies, artifact/evidence, next action and any execution limit. Distinguish accepted work, implemented-but-unverified work, open work and blocked work. A build number, passing test count or worker summary alone does not establish acceptance.

## Execute and review

1. Choose the highest-value unblocked milestone from the user's request. Prefer a complete useful journey when isolated features would leave the requested outcome incomplete. Do not expand scope merely to keep workers busy.
2. Assign one bounded work package: locked inputs, allowed edits, expected deliverable and observable acceptance checks. Keep a single integration owner and one writer per mutable surface. Delegate independent work when useful; respect available capacity and project limits. Keep tightly coupled work sequential.
3. Complete authorized work without repeated permission requests. Continue independent work around a blocked dependency. Ask only when a missing decision materially changes the result or the next action lacks authorization.
4. Inspect the actual result and run checks proportional to the claim. Use independent review for complex or consequential changes when it adds confidence. Preserve domain gates: a timer or checklist cannot advance failed source, financial, native-app or release checks. Keep evaluation answers and prior grading out of isolated evaluation workers.
5. Accept, repair, change approach or record a blocker, then update the backlog. Repeated attempts with no new evidence require a different strategy or an honest stop on that item. Once a milestone passes its relevant checks, stop polishing it and return to step 1 for the next authorized, unblocked milestone. Continue within your assigned scope until its requested outcome is met or an execution limit applies; bounded workers return their completed assignment to the manager. Broaden testing only for changes, failures or unresolved concerns.

## Recover and continue

At a meaningful phase boundary, record the current objective, verified artifacts, decisions, unresolved issues and next action in the existing project checkpoint. Use exact paths and versions where identity matters. Refresh this checkpoint when the scope or owner changes. A checkpoint is a recovery record, not a request for renewed permission: write it and continue in the same turn while authorized work remains. Give routine progress updates while continuing the work rather than stopping at each milestone.

Use a fresh subagent when accumulated context, a new specialty or a clean evaluation boundary makes that useful. Give it the minimum sufficient handoff and verify the prior worker's final state; do not leave competing writers. Creating a separate user-owned task requires the user's request. A handoff can continue in the current task.

On interruption or retry, verify and adopt existing work before creating or sending anything again. Check the available work status before retrying; avoid repeatedly checking an unchanged state. Report meaningful completed outcomes, changed priorities, blockers and decisions in concise language.

## Completion and execution limits

Finish when the user's outcome meets its acceptance checks. At cancellation, a stated deadline/budget, or an unresolved boundary, stop the affected work and leave an accurate checkpoint. For a blocker, identify the exact dependency, supporting evidence and action needed to resume. Distinguish a blocked implementation step from a pending acceptance or release check; continue work that does not depend on that check. Stop the whole task for a blocker only when no useful authorized work can proceed. A time limit does not make partial work complete. If no overall limit is supplied, work in bounded milestones and reassess progress rather than inventing an indefinite campaign.

This skill does not itself schedule background execution. Use supported automations only when the user requests scheduled continuation, and reuse the exact existing owner/automation when already authorized. Preserve its source scope, notification intent and stop conditions. Do not create a competing manager, expand permissions, or imply unattended execution from a written plan.
